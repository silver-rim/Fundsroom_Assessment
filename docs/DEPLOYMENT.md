## 1. The shape of it

Three services, three providers, all free:

```text
   Browser
      │  https
      ▼
  ┌─────────────────┐   VITE_API_BASE_URL (baked in at build time)
  │  Vercel         │───────────────────────────────┐
  │  static SPA     │                               │
  └─────────────────┘                               ▼
                                          ┌─────────────────┐
        CORS_ORIGINS ────────────────────▶│  Render         │
        (the API must name the SPA origin)│  Express API    │
                                          └────────┬────────┘
                                                   │ DATABASE_URL (TLS)
                                                   ▼
                                          ┌─────────────────┐
                                          │  Neon           │
                                          │  PostgreSQL     │
                                          └─────────────────┘
```

**Why this split.** The frontend is a pile of static files after `vite build` — it needs a CDN, not a
server, and Vercel does that for nothing. The backend is a long-lived Node process that holds a
connection pool, which is a poor fit for serverless functions (every cold invocation would open its
own connections and exhaust a free Postgres tier), so it runs as an ordinary web service on Render.
The database is on Neon rather than Render because **Render's free PostgreSQL expires after 30 days**
and a case study that dies a month after submission is not a deployment.

**Deploy in this order** — database, backend, frontend, then close the CORS loop. Each step needs a
value produced by the previous one.

## 3. Step 1 — The database (Neon)

1. **Create a project.** Pick the region closest to where the API will live — you will choose the
   same region for Render in step 2. A cross-region query pays the round trip on *every single call*,
   which is the difference between a 5 ms and a 250 ms dashboard.
2. Neon shows a connection string:

   ```text
   postgresql://USER:PASSWORD@ep-something-12345.ap-southeast-1.aws.neon.tech/neondb?sslmode=require
   ```

3. **Copy it now** — the password is shown once. Keep the `?sslmode=require` suffix.

That is the whole database step. You do **not** need to create tables: the migration runner does it
on the first deploy.

> **If your password contains `@`, `:`, `/`, `?`, `#` or `%`**, it must be percent-encoded in the URL
> (`@` → `%40`), or the driver reads everything before the last `@` as the username and the host
> comes out wrong. Neon's generated passwords are URL-safe, so this only bites when you set your own.
> The same trap is documented in `backend/.env.example` for local installs.

## 4. Step 2 — The backend (Render)

The repository ships [`render.yaml`](../render.yaml), so the service is defined in version control
rather than clicked together in a dashboard nobody can review.

### Option A — Blueprint (recommended)

1. Render → **New** → **Blueprint** → connect the repository.
2. Render reads `render.yaml` and proposes a `mini-erp-crm-api` web service.
3. It will prompt for the two variables marked `sync: false`:
   - `DATABASE_URL` — the Neon string from step 1
   - `CORS_ORIGINS` — you do not have the Vercel URL yet. Put `http://localhost:5173` for now and
     fix it in step 5.
4. **Apply.** The first deploy takes a few minutes.

`JWT_SECRET` is generated by Render (`generateValue: true`) and never leaves the dashboard — nobody,
including you, needs to see it.

### Option B — Manual web service

If you would rather not use a Blueprint, create a **Web Service** and set:

| Setting | Value |
| --- | --- |
| Root directory | `backend` |
| Runtime | Node |
| Build command | `npm ci && npm run build` |
| Start command | `npm run migrate:prod && npm start` |
| Health check path | `/api/health` |

Then add every variable from the table in [§8](#8-environment-variables) by hand.

### What happens on deploy

```text
npm ci             → installs exactly what package-lock.json pins
npm run build      → tsc -p tsconfig.build.json && copy-assets
                     (the test suite is excluded from the build — see §10)
npm run migrate:prod → applies pending .sql files, each in its own transaction
npm start          → node dist/server.js
```

`server.ts` verifies the database is reachable **before** it listens, and exits non-zero if it is
not. A deploy with a bad `DATABASE_URL` therefore fails at startup with a readable log line instead
of booting and serving confusing 500s.

Migrations run in the **start** command, not the build command: the build environment is not
guaranteed to reach the database, and the runner is idempotent, so the restarts a free instance
performs re-run it as a no-op.

**Check the log.** A healthy first deploy ends with:

```text
INFO  Applying 2 migration(s) {"pending":["001_init.sql","002_customer_mobile_partial_unique.sql"]}
INFO  Migrations complete {"applied":2}
INFO  Database connection established {"latencyMs":71}
INFO  API server started {"port":10000,"environment":"production","corsOrigins":["..."]}
```

Now confirm it from outside:

```bash
curl https://mini-erp-crm-api.onrender.com/api/health
# {"success":true,"data":{"status":"ok",...,"database":{"status":"up","latencyMs":2}}}
```

Copy that base URL — the frontend needs it next.

## 5. Step 3 — The frontend (Vercel)

1. Vercel → **Add New** → **Project** → import the repository.
2. **Set the Root Directory to `frontend`.** Vercel then picks up
   [`frontend/vercel.json`](../frontend/vercel.json) and detects Vite automatically.
3. Add the environment variable **before the first build**:

   | Name | Value |
   | --- | --- |
   | `VITE_API_BASE_URL` | `https://mini-erp-crm-api.onrender.com/api` — the Render URL, **including `/api`**, no trailing slash |
   | `VITE_APP_NAME` | `Mini ERP + CRM` (optional) |

4. **Deploy.**

> ### The one thing people get wrong here
>
> **`VITE_API_BASE_URL` is compiled into the JavaScript bundle, not read at runtime.** You can see it
> in a local build:
>
> ```bash
> cd frontend && npm run build
> grep -o "http://localhost:4000/api" dist/assets/*.js   # → one hit, hard-coded
> ```
>
> Changing the variable in the Vercel dashboard therefore does **nothing** to an existing
> deployment — you must trigger a **redeploy** so the bundle is rebuilt. If the deployed app is
> calling the wrong API, this is almost always why.

### Why `vercel.json` exists

The app uses `BrowserRouter`, so `/customers/12` is a client-side route with no file behind it.
Without a rewrite, refreshing that page asks Vercel for a file called `customers/12`, and Vercel
answers 404 — the app appears to break on refresh and on every shared deep link. The config rewrites
every path to `index.html` and lets React Router take over. Static files still win over the rewrite,
so hashed assets under `/assets/` are served normally — and are cached for a year, since their names
change whenever their contents do. `index.html` itself is `no-cache`, so a redeploy is picked up
immediately rather than after a browser cache expires.

## 6. Step 4 — Close the CORS loop

You now have the Vercel URL. Go back to **Render → Environment** and set:

```text
CORS_ORIGINS = https://your-app.vercel.app
```

Exactly the origin: scheme + host, **no trailing slash**, no path. Multiple origins are
comma-separated. Saving restarts the service.

This is the step that gets skipped, and it produces the most confusing symptom in the whole project:
**Postman works, the browser does not.** Postman sends no `Origin` header, so CORS never applies to
it; the browser does, the API does not recognise it, and the request fails before your code ever
runs. The API logs `Blocked a cross-origin request {"origin":"..."}` when this happens — check the
Render log before suspecting the frontend.

Vercel gives every deployment its own preview URL (`your-app-abc123.vercel.app`). Those are **not**
covered by the production origin. Either add the ones you care about to `CORS_ORIGINS`, or test
against the stable production URL.

## 7. Step 5 — Demo accounts on the production database

A fresh production database has the schema but no users, so nobody can log in. The case study
requires working test logins for all four roles, so seed it **once**, deliberately:

1. Render → **Environment**, set:

   ```text
   ALLOW_PRODUCTION_SEED = true
   SEED_ADMIN_PASSWORD     = <a password you choose>
   SEED_SALES_PASSWORD     = <a password you choose>
   SEED_WAREHOUSE_PASSWORD = <a password you choose>
   SEED_ACCOUNTS_PASSWORD  = <a password you choose>
   ```

2. Render → **Shell** (or a one-off job) → `npm run seed:prod`
3. **Set `ALLOW_PRODUCTION_SEED` back to `false`.**

`seed.ts` refuses to run when `NODE_ENV=production` unless that flag is explicitly set, so demo data
cannot reach a production database by accident — for example from a stray `npm run db:setup` in a
deploy hook. The seed is idempotent: running it twice does not duplicate anything.

Set real passwords rather than accepting the development defaults. They are documented in the README
and in this repository, which means they are public.

## 8. Environment variables

### Render (backend)

| Variable | Required | Production value | What it does |
| --- | :---: | --- | --- |
| `NODE_ENV` | ✅ | `production` | Drops stack traces from error responses, switches the request log to `combined` |
| `PORT` | — | *(injected by Render)* | `server.ts` reads it; do not set it yourself |
| `DATABASE_URL` | ✅ | Neon connection string | The only thing that knows where the data lives |
| `DATABASE_SSL` | ✅ | `true` | Required by every managed provider. `false` locally |
| `DATABASE_POOL_MAX` | — | `5` | Free Postgres tiers cap connections; a free Render instance is one process |
| `JWT_SECRET` | ✅ | *(generated)* | Signs tokens. ≥ 32 chars enforced at boot. Changing it logs everyone out |
| `JWT_EXPIRES_IN` | — | `8h` | Token lifetime — one working day |
| `CORS_ORIGINS` | ✅ | `https://your-app.vercel.app` | Browser origins allowed to call the API |
| `BCRYPT_SALT_ROUNDS` | — | `10` | Higher is slower to log in, not meaningfully safer here |
| `LOG_LEVEL` | — | `info` | `debug` while diagnosing |
| `ALLOW_PRODUCTION_SEED` | — | `false` | The safety catch on §7 |

The API validates all of this at boot ([`config/env.ts`](../backend/src/config/env.ts)) and **exits
with a readable message** if something is missing or malformed, rather than failing hours later on
some unlucky request.

### Vercel (frontend)

| Variable | Required | Production value |
| --- | :---: | --- |
| `VITE_API_BASE_URL` | ✅ | `https://mini-erp-crm-api.onrender.com/api` |
| `VITE_APP_NAME` | — | `Mini ERP + CRM` |

Everything prefixed `VITE_` is inlined into a public bundle. **No secret ever belongs here** — not a
database URL, not a JWT secret, not an API key.

## 9. Verifying the deployment

Do not trust a green checkmark on a dashboard. Prove it end to end:

```bash
API=https://mini-erp-crm-api.onrender.com/api

# 1. The API is up and can reach the database
curl -s $API/health
# {"status":"ok", ... "database":{"status":"up","latencyMs":2}}

# 2. Login works against the seeded production accounts
TOKEN=$(curl -s -X POST $API/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"admin@fundsroom.local","password":"<your seeded password>"}' \
  | node -pe "JSON.parse(require('fs').readFileSync(0,'utf8')).data.token")

# 3. An authenticated read returns real data
curl -s $API/dashboard/summary -H "Authorization: Bearer $TOKEN"
```

Then the whole API surface at once, using the Phase 8 collection:

```bash
npx newman run postman/Mini-ERP-CRM.postman_collection.json \
  -e postman/Mini-ERP-CRM.postman_environment.json \
  --env-var baseUrl=https://mini-erp-crm-api.onrender.com/api \
  --env-var rootUrl=https://mini-erp-crm-api.onrender.com
```

56 requests, 144 assertions. Note that this **writes to whatever database it points at** — it
creates a customer, a product and a few challans. That is fine for a demo database and is exactly
how the Phase 8 examples were produced, but do not aim it at anything you care about.

Finally, in a browser:

1. Open the Vercel URL, sign in.
2. Navigate to a customer, then **hard-refresh the page**. If it 404s, the rewrite in §5 is not in
   effect.
3. Confirm a challan, and check the product's stock fell by the quantity sold.
4. Open **System status** in the sidebar — it reports whether the browser can reach the API and
   whether the API can reach the database, which localises a failure in one glance.

## 10. Operational notes

**Free-tier cold starts.** A free Render service is spun down after a period of inactivity, and the
next request has to wait for the process to boot — expect roughly a minute for the first hit on an
idle service, then normal speed. The frontend's loading states cover it, but a reviewer opening the
link cold should be told to be patient. Keeping it warm with an uptime pinger is the usual dodge;
paying for the smallest instance is the honest fix. Neon's compute also autosuspends when idle, but
it resumes in well under a second and is not something a user notices.

**The production bundle contains only what serves traffic.** `npm run build` uses
[`tsconfig.build.json`](../backend/tsconfig.build.json), which excludes `src/tests`. Before Phase 9
the build compiled the test suite into `dist/` and shipped it — including the fixture helper whose
`resetDatabase()` truncates every table. Nothing at runtime imported it, but a TRUNCATE helper has
no business sitting on a production server. Type checking still covers the tests: `npm run typecheck`
uses the base config.

**Source maps are published.** `vite.config.ts` sets `sourcemap: true`, so the frontend's original
TypeScript is readable from the deployed site. That is deliberate for a case study — it makes the
work inspectable, and the bundle contains no secrets. For a commercial product, turn it off or
upload the maps to an error tracker instead of the CDN.

**Redeploys.** Both platforms auto-deploy on a push to the connected branch by default. Render keeps
previous deploys and offers a one-click rollback; Vercel keeps every
build and lets you promote an older one to production. Neither rolls the *database* back — a
migration is forward-only by design, so undoing a schema change means writing a new numbered `.sql`
file, which is what actually happens in production.

**Logs.** The API logs structured JSON in production (one object per line), so Render's log search
works on field values. 5xx responses log a stack trace; 4xx log a single warn line, because a client
being told "no" is normal traffic, not an incident.

## 11. Troubleshooting

| Symptom | Almost certainly |
| --- | --- |
| Browser console: *blocked by CORS policy* | `CORS_ORIGINS` on Render does not exactly match the Vercel origin. No trailing slash, no path. The Render log confirms it: `Blocked a cross-origin request` |
| Postman works, the browser does not | The same thing. Postman sends no `Origin` header, so CORS never applies to it |
| The deployed app calls `localhost:4000` | `VITE_API_BASE_URL` was set after the build. Trigger a redeploy — the value is compiled in (§5) |
| Refreshing a deep link 404s | The rewrite is missing: Root Directory is not `frontend`, so `vercel.json` was never read |
| Deploy log: *Invalid environment configuration* | A required variable is missing or malformed; the message names the exact field. See §8 |
| Deploy log: *Could not connect to the database* | `DATABASE_URL` wrong, or `DATABASE_SSL` is not `true` for a hosted provider |
| `password authentication failed` with an obviously correct password | An unescaped `@`, `:` or `%` in the connection string (§3) |
| `/api/health` returns 503 with `"database":{"status":"down"}` | The API is alive but Postgres is not reachable — Neon project suspended, deleted, or the credentials were rotated |
| First request takes ~a minute, then everything is fast | Free-tier cold start (§10). Not a bug |
| 401 on every request right after a deploy | `JWT_SECRET` changed, which invalidates every issued token. Log in again |
| Login returns 401 with correct credentials | The production database was never seeded (§7) |
| Migration failed mid-deploy | Each file runs in its own transaction, so the database is unchanged by the failing file. Fix the SQL, push, redeploy |

## 12. What would change for a real production system

This deployment is honest about being a case study on free tiers. Before it carried real customer
data:

- **Rate limiting** on `/api/auth/login` at minimum — there is none today.
- **A paid instance**, so there are no cold starts and no single-process ceiling.
- **Managed backups with a tested restore.** Neon's free tier has limited history; nobody has a
  backup until they have restored one.
- **An error tracker** (Sentry or similar) rather than reading logs after a user complains.
- **Refresh tokens and a revocation list.** Today a token is valid for its full 8 hours and
  deactivating a user takes effect at their next login — a documented trade-off of keeping the API
  stateless, and the right thing to revisit first.
- **A custom domain with HSTS**, and `CORS_ORIGINS` narrowed to it.
- **Staging.** One environment is one environment; every deploy is currently to production.
